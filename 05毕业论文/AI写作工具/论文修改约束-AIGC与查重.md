# 本科毕业设计（论文）修改约束：AIGC 与查重（通用模板）

本文档用于**任意工科类毕设论文**在 AI 辅助润色、降重、定稿前的统一口径。  
适用对象：嵌入式、物联网、自动化、计算机、电子等以**系统设计与实验验证**为主的毕业设计。

**重要说明：** 查重率与 AIGC 疑似率由不同算法、不同库、不同阈值策略产生，**二者不必然同向变化**。一份文稿可以「查重偏高、AIGC 偏低」，也可以相反。本文档的目标是：**在事实可核查的前提下，同时降低连续相似片段与模板化写作风险**，而不是追求某一平台的固定百分比。

---

## 一、两类检测分别在看什么

| 维度 | 常见关注点 | 容易命中的写法 | 相对安全的写法 |
| --- | --- | --- | --- |
| **文字查重** | 与已有文献、学位论文、网络资料的**连续相同或高度相似** | 教材式定义、器件手册复述、国内外现状套话、他人论文句式 | 写清**本课题如何用、如何接、如何测**，缩短公共定义 |
| **AIGC 疑似** | 段落**均匀、完整、套话多、缺少个人取舍痕迹** | 「随着…发展」「具有重要意义」「综上所述」、排比句、空洞总结 | 具体对象 + 具体动作 + 条件/限制 + 与实验或源码的对应 |

**经验结论（来自同题两版文稿对比）：**

- **查重偏高**时，常见原因不是「字写得差」，而是**仍像通用论文/说明书**：综述段与网络模板接近、硬件小节按手册顺序复述、测试段反复使用「验证…能够…测试结果显示…满足设计要求」。
- **AIGC 偏低**时，常见特征是**论述绑在本课题**：需求—方案—实现—测试能互相对照，保留适度工程限制（未 OTA、未计量检定、样本量小等），句式不必华丽但信息密度高。

## 二、总目标（通用于所有课题）

1. **事实不变**：器件型号、引脚、协议、关键参数、测试数据、引用编号、图表数据不得为降重而篡改。
2. **归属清楚**：他人观点、厂商方案、教材定义必须能对应文献或公开资料；不得把文献结论写成自己的实测。
3. **降低双风险**：减少「公共知识长抄」与「AI 模板腔」；**优先改论述角度与信息结构，再改用词**。
4. **保持本科尺度**：可写清调试过程、课设/实验室条件、样机局限；不夸大为商用产品或行业认证水平。
5. **章节互证**：需求章写的条目，应在硬件、软件、测试章出现**可核对**的落实方式。

## 三、不可改动的硬约束（使用前请自行填入）

> 将下列占位符替换为你的课题实际内容，整篇论文全文统一。

### 3.1 专业术语与专有名词

- 芯片/平台：`{如 STM32F407、FreeRTOS、Linux 等}`
- 模块与协议：`{如 MQTT、SPI、I2C、Modbus 等}`
- 第三方平台：`{如 OneNET、阿里云 IoT 等}`

**规则：** 首次出现宜写全称或中英对照；后文用简称，**不得**为降重随意换成非行业通用别称。

### 3.2 代码与工程标识（若论文涉及软件实现）

- 任务/线程名：`{app_task_xxx}`
- 全局变量、队列、信号量、互斥锁：`{g_xxx}`
- 关键函数名：`{xxx_init、xxx_get_xxx}`
- 通信指令、JSON 字段、AT 指令：**与源码、协议文档一致**

**规则：** 标识符**不因降重而改名**；可在正文用中文解释其职责，但符号保持原样。

### 3.3 关键数据与结论边界

列出本课题**已测试或已在设计中固定**的数据，例如：

- 采样周期、超时时间、量程、精度、运行时长
- 表格中的「设计要求 / 实测结果」
- 引用文献编号与对应观点

**规则：** 不得新增未做实验的指标；不得把「课程样机」写成「已量产应用」。

### 3.4 引用与图表

- 文献 `[n]` 不得张冠李戴。
- 公式、引脚表、接线表、测试表**不为降重重排数字或单位**。
- 图题、表题符合学校格式，不为降重改成非规范标题。

## 四、查重率偏高的典型原因与改法

### 4.1 高风险章节（几乎所有工科毕设通用）

| 章节 | 为何易重复 | 改写原则 |
| --- | --- | --- |
| 绪论·背景 | 与海量「智能家居/物联网/嵌入式」综述雷同 | 从**具体场景痛点**切入，少写行业宏大叙事 |
| 国内外现状 | 企业名+技术名词堆砌，句式与知网论文相似 | **一篇文献一句主贡献**，区分「他人工作 / 本文工作」，文献观点要有 `[n]` |
| 器件/协议介绍 | 照搬手册、教材、CSDN 教程 | **只写本设计用到的引脚、时序、阈值**；定义压缩到 1～2 句 |
| 硬件电路 | 「电源+复位+晶振+SWD」固定段落 | 调整叙述顺序（先功能后引脚，或先软件读法后硬件），**引脚与参数不改** |
| 测试 | 「测试结果显示…满足设计要求」连环句 | 写**条件 + 操作 + 现象 + 数据**，弱化万能结论 |

### 4.2 无效降重（易适得其反）

1. **纯同义词替换**：信息不变，易被判定为刻意规避，且术语可能写错。  
2. **打乱语序但逻辑更差**：可读性下降，查重未必下降。  
3. **大量插入无意义字词**：影响导师评阅，对 AIGC 也无益。  
4. **把引用内容改写成无标注的自己的话**：学术风险高于查重风险。

### 4.3 有效降重（推荐顺序）

1. **删**：与本设计无关的百科背景、过长协议介绍。  
2. **缩**：公共概念只保留后文要用到的那一段。  
3. **绑**：每段至少出现一项**本课题独有信息**（引脚、任务分工、测试条件、失败现象）。  
4. **换角度**：从「是什么」改为「在本系统中用来做什么、与哪一章对应」。  
5. **拆合句**：长句拆短或合并，改变 n-gram 连续匹配，**不改变事实**。

## 五、AIGC 疑似偏高的典型原因与改法

### 5.1 高风险句式（全文慎用，不宜密集出现）

- 随着……的不断发展 / 在……背景下  
- 具有重要意义 / 具有广阔应用前景  
- 有效提高了…… / 显著增强了……  
- 综上所述 / 本文首先……其次……最后……  
- 测试结果表明……满足设计要求（无数据支撑时）  
- 从根本上解决 / 全面实现了 / 高内聚低耦合（无具体机制时）

### 5.2 推荐替换思路（通用）

| 空泛写法 | 可改为 |
| --- | --- |
| 该系统实现了多功能集成 | 列出**具体模块 + 接口 + 由哪个任务/模块负责** |
| 有效提高了实时性 | 写**通知路径**（中断/信号量/队列）及**测试中观察到的时间量级** |
| 满足设计要求 | 写明满足**哪一条需求/表格哪一行** |
| 具有良好的稳定性 | 写**连续运行时长、是否复位、异常现象** |

### 5.3 让文本更「像自己写的」（不必故意写错）

1. **主语具体化**：少写「系统」「该方案」，多写器件、任务、引脚、平台名。  
2. **保留合理限制**：固定 WiFi、无 OTA、未做电流测试、样本量少等——比全篇优点更像真实毕设。  
3. **句长参差**：避免连续三句同一开头（「系统能够…」「通过…实现…」）。  
4. **章间指代**：用「见第×章」「与表×-×一致」「与源码中××对应」，代替空洞衔接词。  
5. **测试语言克制**：「约」「量级」「在本次条件下」「未做大样本统计」优于绝对化承诺。

### 5.4 不建议的「去 AI」手段

- 故意错别字、网络梗、过度口语（「板子」「绝了」等）——除非全文风格统一且导师接受。  
- 编造未做的实验或夸大指标。  
- 把技术章节改成散文，损失可复核性。

## 六、分章节通用写作约束（与具体课题无关）

### 摘要

- 结构建议：**背景 1 句 → 本设计做了什么（硬件+软件+通信）→ 关键机制 1～2 句 → 测试结论（带数据量级）**。  
- 避免：空泛「智能化水平」「应用前景」。

### 绪论

- 背景：从**用户/场景问题**写，少写全球产业趋势长段。  
- 现状：**文献归属清晰**；企业产品写「边界参照」，不写成本文创新。  
- 本文工作：与后文章节**一一可对应**，避免「本文主要研究了…」后接一串名词。

### 需求分析与方案

- 需求宜**可验收**（谁用、上电后什么状态、异常时什么现象）。  
- 方案比选：缺点要联系**本课题资源约束**（单芯片、周期、已有源码），不要只写教科书优缺点表。

### 硬件设计

- 选型：写**为何对本设计够用**，少抄手册性能列表。  
- 电路：引脚、电压、公式**准确第一**；句式可从「怎么测、怎么读」切入。

### 软件设计

- 写清**模块划分、数据流、同步手段**（中断、RTOS 对象、状态机等）。  
- 避免把操作系统写成「提高效率的工具」而无实例。

### 测试与总结

- 测试：**条件 + 步骤 + 现象 + 数据**；结论与表格、需求对应。  
- 结论：成果与不足**都要写**；创新点不宜满篇「首次」「领先」。

### 致谢

- 自然书面语即可，避免模板化排比感谢。

## 七、处理强度定义

### light（轻度润色）

- 适用：导师基本认可，仅需降低套话、理顺句读。  
- 保留约 **90%** 结构与段落划分。  
- 只改连接词、重复句式、明显 AI 套话。  
- **不**新增技术结论。

### deep（深度改写）

- 适用：查重片段集中，或段落明显模板化。  
- 保留观点、数据、引用编号、结论方向。  
- 可调整段内顺序：概念介绍 → 工程选择 / 测试对应。  
- 公共知识改为「在本设计中的作用」。

### academic（学术克制）

- 适用：摘要、绪论、结论、答辩定稿。  
- 更严谨、少夸张；术语与引用规范。  
- 创新点、价值表述需有**设计或测试依据**。

**默认：** 未指定时用 `light`。  
**篇幅：** 一般控制在原文 **±10%**；若原文空话过多可略压缩，**不删必要技术信息**。

## 八、AI 改写通用提示词（复制后替换占位符）

```
你是一位熟悉工科毕业设计论文写作的学术编辑。请在不改变专业术语、关键数据、引用编号、实验结论和章节结构的前提下，对下面这段论文文字进行改写。

课题类型：{嵌入式系统 / 物联网 / 控制系统 / 其他}
检测侧重：{查重 / AIGC / 二者兼顾}
处理模式：{light / deep / academic}

硬约束：
1. 保留以下专有名词与标识符不变：{列出芯片、协议、任务名、变量名等}
2. 保留所有测试数据、周期、误差、引脚号、公式与表格结论不变
3. 保留文献编号 [n]，不得虚构新文献
4. 不得新增未经验证的性能指标；不得把样机写成商用产品

改写要求：
- 优先降低与教材/网络教程的连续相似表述（查重）
- 降低「随着…发展」「具有重要意义」「综上所述」「测试结果表明…满足设计要求」等模板句（AIGC）
- 公共概念改为「在本设计中的用途与连接方式」
- 先改论述结构与信息顺序，再改用词；避免机械同义词替换
- 输出仅给改写后的正文，不要修改说明、不要列表对比
- 篇幅控制在原文 ±10%，段落数量尽量不变

原文：
{text}
```

## 九、定稿前人工复核清单

- [ ] 术语、型号、引脚、协议名是否被误改  
- [ ] 数据、周期、精度、延迟、运行时间是否与源码/实验记录一致  
- [ ] 代码标识符、指令格式、JSON 字段是否一致  
- [ ] 文献 `[n]` 是否与句中观点匹配  
- [ ] 是否新增未做过的功能或测试  
- [ ] 是否出现过度宣传、绝对化结论  
- [ ] 同一段是否句式过于整齐、连接词过密  
- [ ] 需求—实现—测试是否能在章间对应  
- [ ] 不足与限制是否仍保留（避免「完美系统」腔）  
- [ ] 摘要与结论是否与正文数据一致

## 十、两版文稿差异的对照启示（方法论，非保证结果）

当**同题两版**出现「AIGC 很低、查重很高」或相反情况时，可按下表自查：

| 现象 | 可能原因 | 建议动作 |
| --- | --- | --- |
| 查重高、AIGC 低 | 文字像「规范论文」，但与知网/手册重合多 | 压缩综述与器件百科；加强本设计专属叙述 |
| 查重低、AIGC 高 | 改写后仍太整齐、套话残留 | 拆排比；补测试条件与限制；章间具体指代 |
| 二者都高 | 大段未改动的网络/教材原文 + AI 润色 | 先人工删百科，再 deep 改写，最后 academic 定稿 |
| 二者都低 | 已较好绑定课题且事实准确 | 仅 light 润色，避免过度改写引入新风险 |

## 十一、免责声明

各高校、各检测平台（维普、知网、Turnitin、校内自建库等）的算法与阈值会调整，**任何写作约束都不能保证固定的查重率或 AIGC 百分比**。  
本文档用于统一改写标准，使论文**更具体、可核查、更符合本科毕设尺度**，并降低因盲目降重导致的事实错误与学术不规范风险。
